# 0018 — OpenTelemetry GenAI conventions from the runner and the gateway

- **Status**: proposed, 2026-09-25 — not implemented
- **Concerns**: the runner, LiteLLM, the API and orchestrator logging, `infra/bootstrap/otel-collector.yaml`

## Context

An OpenTelemetry collector is installed by Argo CD in wave 2 (`monitoring` namespace,
daemonset mode). Nothing sends it a span. Since P0-4 the API and the orchestrator expose
Prometheus metrics and log with `structlog` (request id, `project`, `work_item`, `run_id`,
`stage`), but a run is still read as a list of journal rows, not as a trace.

The OTel **GenAI semantic conventions** (`gen_ai.*`, status *Development* in 2026) name the
spans we need: `invoke_agent`, `execute_tool`, and the client spans for model calls with
`gen_ai.usage.input_tokens` / `output_tokens` and `gen_ai.request.model`. LiteLLM emits the
client spans natively through its OTel callback.

## Decision

1. **One trace per run.** The orchestrator opens a span `invoke_workflow` per stage attempt,
   propagates the context to the Job through the environment (`TRACEPARENT`), and the runner
   opens `invoke_agent` for the ACP session. Every MCP call through the sidecar becomes an
   `execute_tool` span (name, duration, `is_error`, the catalogue tool's provider, never its
   arguments).
2. **Model calls are the gateway's spans**, not the runner's. LiteLLM's OTel callback is
   enabled in the embedded chart with the run id as `gen_ai.conversation.id`; the runner
   never sees the request and never invents token counts.
3. **The ledger stays the truth for money** (ADR 0004). Traces carry `gen_ai.usage.*` for
   reading, and a nightly job compares the sum of a run's trace usage with its ledger rows;
   a drift is a finding on the platform, not a correction of the ledger.
4. **Correlation keys are the structlog keys.** `run_id`, `work_item`, `project`, `stage`
   go on every span as attributes, so a log line and a span meet on the same values.

## Conditions

- The conventions are in Development: attribute names may change. The semconv version is
  pinned in one module (`choregos_core.telemetry`), and only that module knows the names.
- No gate reads a span. A guarantee is a mechanism on data the platform holds (ADR 0010);
  a trace can be sampled, dropped or late.
- The agent's prompt and the tool arguments are **not** recorded on spans: the journal already
  holds what the evidence pack needs (ADR 0015), and the collector's retention is not ours to
  audit.

## Consequences

- A run reads as a tree: stage → agent session → tools and model calls, with durations. The
  "why did this stage take 40 minutes" question gets an answer from Jaeger or Tempo instead
  of a psql query on the bench.
- The dashboards that P0-4 pruned back to exposed metrics can gain RED panels per stage from
  span metrics, generated by the collector — still no orphan panel.

## Alternatives discarded

- **Writing our own trace format into `run_events`**: the journal is the durable record and
  stays; duplicating it as a proprietary trace gives nothing a collector does not.
- **Instrumenting the agent itself** (Claude Code, Codex, Gemini CLI): the agents are
  black boxes by design (ADR 0002, BYO agent); we measure their edges, not their insides.
