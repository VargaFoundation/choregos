# 0161 — The GitHub App is created from a manifest, by the instance's operator

- **Status**: proposed, 2026-11-12; S70-21 implements it
- **Concerns**: `routers/github_app.py` (`/platform/github-app`, `/platform/github-app/manifest`,
  `/github/manifest/callback`), `services/github_app_credentials.py`, `services/github_app_manifest.py`,
  the table `github_app_registrations`, the readers of the App (`services/github_app.py`,
  `routers/internal.py` git token, `routers/webhooks.py`, `knowledge/sync.py`,
  `routers/knowledge/source_config.py`, `routers/admin.py` rewrap), `choregos_adapters.github.manifest`
  and `builtins._github_client`, the console page *Administration → GitHub App*, the contract
  (`openapi.yaml`); amends [ADR 0073](0073-github-app-installations-are-discovered-not-typed.md), which
  deferred the manifest flow; uses [ADR 0058](0058-connector-secrets-are-write-only-values.md) to seal

## Context

One GitHub App serves a deployment (ADR 0073 §5): its id, private key, webhook secret and OAuth client
are deployment settings (`github-app-id`, `github-app-private-key`, `github-webhook-secret`,
`github-app-client-id`, `github-app-client-secret`). The operator created it by hand on github.com,
copying a permission table and five URLs, then put four values in a Kubernetes Secret. Three problems:

- **Whoever creates the App owns it.** An App belongs to the GitHub account that registered it, and an
  App has one webhook URL, so one App serves one deployment. An installation of Choregos must be able to
  create *its own* App, owned by *its* operator, without borrowing another operator's.
- **The permissions drift.** `docs/deployment.md` listed Contents, Issues, Pull requests and Checks plus
  Metadata, and the events without `projects_v2_item` and `check_run`, while the adapters' own list
  (`APP_PERMISSIONS`, `APP_EVENTS`, compared with the procedures by `tests/procedures/`) also asks for
  `statuses: read` and `organization_projects: write`. An App made from the page missed two of them.
- **Four secrets by hand.** The webhook secret had to be invented and typed twice (GitHub, Secret); the
  OAuth client needed for claims on a several-organisation instance was a later, separate gesture.

GitHub's App Manifest flow does all of it in one round trip (verified against GitHub's documentation on
2026-11-12: "Registering a GitHub App from a manifest" and the REST reference "Create a GitHub App from a
manifest"):

1. a browser POSTs a form with one field, `manifest` (JSON), to `https://github.com/settings/apps/new`
   (a personal account) or `https://github.com/organizations/<org>/settings/apps/new`, with an optional
   `state`; the manifest's keys are `name`, `url` (required), `hook_attributes` (`url` required,
   `active`), `redirect_url`, `callback_urls` (ten at most), `setup_url`, `description`, `public`,
   `default_events`, `default_permissions`, `request_oauth_on_install`, `setup_on_update`;
2. GitHub registers the App under the account of the person who confirms, and redirects to
   `redirect_url` with a temporary `code` and the `state`;
3. `POST /app-manifests/{code}/conversions`, unauthenticated, answers 201 with the App (`id`, `slug`,
   `owner`, `name`, `html_url`…) and its credentials `client_id`, `client_secret`, `webhook_secret`
   (generated by GitHub) and `pem`; 404 or 422 otherwise. The three steps complete within one hour.

Also verified there: `installation` and `installation_repositories` are delivered to every App ("All
GitHub Apps receive this event by default. You cannot manually subscribe to this event."), and when
"Request user authorization (OAuth) during installation" is selected no Setup URL can be set: users are
redirected to the Callback URL instead.

## Decision

1. **A platform administrator creates the App from the console.** *Administration → GitHub App* posts
   GitHub the manifest the API builds (`POST /platform/github-app/manifest` answers the form's
   `action_url` and `manifest`). The owner is the person's account, or a GitHub organisation they name.
   **Public or private is an explicit choice**: the request has no default for `public`, and the form
   preselects neither.
2. **The manifest is derived, never typed.** `url` is the console's public URL; `hook_attributes.url`
   `<api_url>/api/v1/webhooks/github` (`active` false when GitHub cannot reach the instance);
   `redirect_url` `<api_url>/api/v1/github/manifest/callback`; `callback_urls` the existing Setup route
   `<api_url>/api/v1/github/setup`, with `request_oauth_on_install: true`, so the person who installs the
   App authorises it and a several-organisation instance can check they manage the installation (ADR
   0073 §4) — no `setup_url`, which GitHub refuses alongside that option. `default_permissions` and
   `default_events` are `APP_PERMISSIONS` and `APP_EVENTS`, the adapters' constants the procedures are
   already compared with: the manifest cannot ask for less, or more, than the platform uses.
3. **The callback checks the state, then the code.** The `state` is signed with the session secret for
   its own purpose (`github-app-manifest`), lives one hour, and names the person who started; the
   callback needs that person's console session as a platform administrator. Everything that would
   prevent storing the App (an App in the deployment's settings, an App already stored, no secrets key)
   is checked **before** the code is exchanged: GitHub answers a code once.
4. **The credentials are sealed where the platform keeps sealed values.** One row of
   `github_app_registrations` (forced RLS, platform scope only) keeps what GitHub publishes in clear and
   one envelope (ADR 0058, `CHOREGOS_SECRETS_KEKS`) holding the private key, the webhook secret and the
   client secret, its additional data bound to the platform and `github-app/<app_id>`. No key, no App:
   409 naming `CHOREGOS_SECRETS_KEKS`. `choregos admin secrets rewrap` moves it to a new key with the
   connector secrets. Audited: `github_app.create`, `github_app.forget`.
5. **One place resolves the App, and the deployment's settings win.** `services/github_app_credentials`
   returns the deployment's settings when they name an App, else the stored one. Every reader goes
   through it: the installations' port, the run's git token, the knowledge sources, the GitHub webhook's
   signature (the stored App's generated secret), and the adapters' GitHub client through a process
   provider (`choregos_adapters.github.set_app_credentials_provider`): the private key never travels in a
   connector configuration or a Temporal payload. A replica caches the stored App and reads it again at
   most every 60 seconds, on the async paths that hold a session (the orchestrator's pinning of a GitHub
   connector included), so another replica learns of a new App within a minute.
6. **Forgetting is local.** `DELETE /platform/github-app` deletes the stored credentials; the App stays on
   GitHub, where its owner deletes it. The deployment's settings are never written by the API.

Rejected:

- **Writing the credentials into the deployment's Kubernetes Secret.** The API would need write access to
  Secrets, and a Secret synchronised from a vault (ExternalSecret) would overwrite them at the next sync.
- **Showing the credentials once for the operator to copy into the Secret.** Back to four values typed by
  hand, and a private key in a browser.
- **One App per organisation** (ADR 0073's deferred option): still deferred. The table holds one App;
  `github_installations.app_id` keeps the column for that day.
- **Keeping `setup_url` and `setup_on_update` with the OAuth option**: GitHub does not accept a Setup URL
  when it asks for user authorization during installation.

## Consequences

- An operator with no App in the deployment's settings creates one in a minute, owned by their own
  account or organisation; the four `github-app-*` entries of the Secret become optional.
- The permission table of `docs/deployment.md` now says what the adapters use, and a test holds it to
  `APP_PERMISSIONS` and `APP_EVENTS`.
- An instance whose deployment names an App keeps it: nothing changes, and the console says why it
  cannot create another.
- Not covered: GitHub Enterprise Server (the manifest and conversion URLs are github.com's), an App per
  organisation, and the transfer of an existing App between accounts (a GitHub setting).
