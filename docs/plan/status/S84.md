# S84 — Desk seams: approvers from the work item, filing into another project, a webhook's sender identity

The status rows of stream S84. The legend and the rule for a new row are in [STATUS.md](../STATUS.md).

| Story | Stream | Status | PR | Notes |
|:--|:--|:--|:--|:--|
| S84-01 | S84 | ✅ | — | **An action's approvers come from its work item** ([ADR 0196](../../adr/0196-an-actions-approvers-come-from-its-work-item.md), proposed). A workflow action's approver `group` may read one declared field (`owners-{{ fields.tool }}`), rendered at proposal; `approval.excluded` names who may not decide, rendered the same way; an excluded person, organisation administrator included, gets `403`; a group field absent or empty refuses the proposal; the validator refuses any other template. **Proves**: `apps/api/tests/test_approvers_from_the_work_item.py` (the rendered group decides, a rank outside it does not, the person concerned and the requester are refused even as administrators, an empty exclusion excludes nobody, three unrenderable rules refuse the proposal, five validator cases). **Does not prove**: a group as a real identity provider sends it (name or object id) at sign-in; the console showing `excluded` (the action DTO carries it). |
| S84-02 | S84 | ✅ | — | **A workflow files a work item in another project** ([ADR 0197](../../adr/0197-a-workflow-files-a-work-item-in-another-project.md), proposed). The core effect `work_item.file` `{project, title, body, labels}` files through the target project's tracker as a person's request is filed (`create_work_item`), answers `{project, key, url, work_item_id}`, is `approval`, files only into a project whose `accepts_items_from` lists the source, labels it `from:<source>` (routing, and an external tracker; an internal one keeps no labels), does not start it, and files nothing twice under the same effect key. **Proves**: `apps/api/tests/test_work_item_file_effect.py` (an external tracker receives one issue and a replay none; an internal target mints its key; not accepted, unknown, same project, no title and not approved file nothing; a non-slug in `accepts_items_from` is refused); template conformance admits the effect. **Does not prove**: a real Jira instance; the replay window between an external issue and its row (ADR 0197 §5); an end-to-end action through `ActionWorkflow` (the effect is played directly, as the HR effects are). |
| S84-04 | S84 | ✅ | — | **A fan-out's children are the platform's** ([ADR 0199](../../adr/0199-a-fan-outs-children-are-the-platforms.md), proposed). `spawn_children` opens each child in the platform under `<parent>.<rank>` (`create_work_item(in_platform=True)`), whatever the project's tracker; `tracker_for` sends nowhere the tracker writes of a child (state, status comment, fields, comments, close) when the tracker keeps its items elsewhere. **Proves**: `apps/orchestrator/tests/test_fan_out.py` (on an external tracker's project, two children opened in the platform, nothing filed, a replay finds them; a child's writes go nowhere on an external tracker and to the internal one otherwise), `apps/api/tests/test_work_item_external_tracker.py` (a child keeps its given key, nothing filed; no key refused). **Does not prove**: a full workflow on a Jira project with a fan-out; findings comments on a child's origin (`findings.py`) still go to the tracker. |
| S84-03 | S84 | ✅ | — | **A plugin server may verify its sender's bearer token** ([ADR 0198](../../adr/0198-a-plugin-server-may-verify-its-sender-s-bearer-token.md), proposed). A server declaration's `webhook.forward_authorization: true` forwards the delivery's `Authorization` header to that server's `tracker_parse_event`; any other server still never sees it; the platform does not log or store it. **Proves**: `apps/api/tests/test_plugin_tracker.py` (a server that did not declare it receives no `Authorization`; one that did receives it, without `Cookie`, and the token is neither in the logs nor in the audit trail). **Does not prove**: a real bot service's token, which the server verifies, not the platform; that a server never echoes the header in an error the platform logs (the server's duty). |
