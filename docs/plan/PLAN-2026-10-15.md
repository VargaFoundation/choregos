# Plan — 2026-10-15: the enterprise edition in production, governed agents, catalogues, a project-first console

Source: the product owner's request of 2026-10-15 (20 items). Each item was checked against the
code at `e24f0d59` (`origin/main` of the day) and, where it touches an outside product (Microsoft
Agent Builder, Atlassian Rovo, MCP registries, skill directories), against what that product
publishes. Stream number: **S39**; story ids `S39-NN` where `NN` is the item number below. A detailed
plan per item (design, steps, tests, overlaps) was written for each story; this page is the summary
that stays in the public repository.

Status words: **exists** (in the code), **missing**, **broken** (exists and is wrong).

Scope note: this repository is public. Items 1, 2, 3 and 18 concern one operator's deployment. They
are described here in generic terms (an enterprise edition published by a third party, deployed on
the operator's hosts, operator theming, a knowledge base about the operator built from public
sources). What belongs to the operator's own infrastructure lives in the operator's deployment
repository, not here.

## 1. Decisions, item by item

### Item 1 — The enterprise edition on the dev instance, published by a third party

**Decision.** The edition names its publisher as data. `GET /edition` gains `publisher` and the EE's
own `version`; the console footer and edition card show them. The EE repository moves to the
operator's organisation, its images are rebuilt for the CE version the instance runs, and the dev
instance switches to them by pinning the immutable `sha-<12>-ce<CE>` tag (the `<version>-ce<CE>` tag
is mutable while the EE is a development version).

**Rejected.** Hard-coding the publisher in the console (it is a fact about a build, not about the
console). Pulling from the public registry directly (private images, and the cluster admits only the
operator's registry). Building the EE web image (nothing EE runs in the browser: sections are data,
ADR 0032).

**Stories.** `S39-01`: one CE `contract(edition)` PR; EE repository changes (rebrand, compatibility
range, publisher field, build for the current CE tag) in the EE's own repository and language; one
operator-platform PR (registry path, credential owner); one deployment PR (switch the instance to the
EE images).

**ADR.** Amends **0024 (two editions)**: "published by the foundation" becomes "published by the
edition's publisher, named in the edition's own metadata"; the trademark note follows.

**Left to the operator.** Transfer the EE repository; confirm Actions, signing keys and package
creation in the new organisation; replace the expired upstream token of the registry proxy (the
measured blocker); merge the platform and deployment PRs; confirm with the foundation that the
publisher may use the product name for the enterprise edition (`docs/TRADEMARK.md`).

### Item 2 — Dev and prod hostnames

**Decision.** Dev is a rename of the existing instance to a new hostname over HTTPS (the old name
redirects). Prod is a **new environment**, which is most of the work and is the operator's platform
work: its own tenant, secrets, a durable workflow engine (not the dev-mode one), backups with their own
credentials, a public GitHub App for webhooks. The CE side is one fix: the session cookie is `Secure`
whenever the public URL is HTTPS, not only when `env` says so.

**Rejected.** Reusing the dev socle for prod (dev-mode Temporal, dev secrets, single values file that
the vendoring script would delete). Serving both hosts from one deployment (the API derives every URL
from one host; the cookie is host-only).

**Stories.** `S39-02`: CE `fix(api)` cookie (2a); operator platform PRs for certificates, DNS and
identity-provider redirect URIs (2b), prod enrolment (2d) and its certificate once the namespace exists
(2f); deployment PRs for dev (2c) and prod (2e), with a prod values file the vendoring script keeps.

**Left to the operator.** Everything outside the CE: DNS records, the internal resolver, certificates,
identity client redirect URIs, secrets for the new environment, the manual prod sync, the prod GitHub
App.

### Item 3 — Theming in the enterprise edition

**Decision.** *The CE exposes a neutral, validated theme seam and renders whatever theme the API
serves; customising it is an enterprise feature; a brand is data of the deployment that wears it.*
- `GET /theme` (public, since sign-in needs it) returns a `Theme`: product name, default mode, **sparse
  hex overrides** of the 52 colour roles per mode, two radii, optional title/sans fonts and a logo,
  favicon and footer text. Assets are same-origin references only (the CSP allows nothing else).
- A provider seam in the API plugin surface: one provider; its result is **validated** (schema plus the
  console's contrast budget on defaults ⊕ overrides) and the CE default is served on any failure.
  The console never breaks because of a theme.
- The console applies it before first paint from the root layout (a nonce'd `<style>`, `@font-face`,
  favicon). The attribution to the foundation is not overridable.
- Chart: generic extra volumes and mounts for the API.
- EE: a deployment theme read at start from a mounted directory (an invalid theme **stops the API**:
  a deployment error must be loud), then editing in the console for the instance and per organisation.
- The operator's theme is a data file built from its public design system; a commercial title font is
  used only if the operator's licence covers it, otherwise titles fall back to the sans font.

**Rejected.** A `theme.css` endpoint (a second representation); a client-only fetch (a flash of the
default look on every navigation); bundling themes in the console (the CE would ship brand code).

**Stories.** `S39-03a` `contract(theme)` provider seam, validator, route; `S39-03b` console applies the
served theme; `S39-03c` chart extra volumes; EE themes (deployment theme, then editing); one
deployment PR carrying the operator's theme. CE release first.

**ADR.** **0064 — A theme is data.**

**Left to the operator.** Font licence confirmation, product-name choice, brand sign-off on light and
dark screenshots, merging the deployment PR.

### Item 4 — The project's Inbox entry

**Decision.** Web only, no API change. The project sidebar's Inbox leads to a project inbox
(`/p/[slug]/inbox`) computed client-side from the three reads the organisation inbox already makes,
narrowed to the project (its items; actions with its `project_slug`; budget alerts scoped to it). The
entry's count is the project's. Tests lock the entry's target, the gap that let the bug through.

**Rejected.** A project filter on the organisation inbox (the sidebar would still switch scope);
a server-side project inbox (nothing to compute that the browser lacks).

**Stories.** `S39-04`: one PR.

### Item 5 — A cleaner "New agent"

**Analysis of Microsoft's Agent Builder.** Relevant: a **Describe** step (a model drafts name,
instructions and sample input), a form with advanced settings hidden, a live test pane beside it, draft
before publish. Not relevant: starter prompts (Choregos agents are stage workers, not chat assistants;
the equivalent is a sample input and one or two eval cases), icons, topics, triggers, channels
(workflows are the triggers), knowledge upload inside the builder (a base is an organisation object
attached by reference). The earlier decision stands: a definition is data with a form on top, not a
visual canvas.

**Decision.** A full page `/agents/new` with a **short first step** (name, what it is for, optional
"Draft it for me"), progressive disclosure of the other sections, a right-hand panel with the existing
trial bench and the cost summary, and "Save as draft" next to "Create and activate". The drafting
endpoint reuses the pattern of the knowledge distiller (a protocol, a deterministic fake, a gateway
implementation, instructions from a catalogue agent). **A draft is never saved**: it fills the form
for a person to review.

**Rejected.** Widening the drawer (the form is still 16 inputs); a chat-style builder; a canvas.

**Stories.** `S39-05`: PR 1 web layout (the visible fix, ships alone); PR 2 `contract(agents)` drafting
endpoint with its catalogue agent and ADR-free reserved slug; PR 3 "Draft it for me" in the web.

### Item 6 — Connectors: pick, don't type; secrets that can be typed

**Decision, part (a).** The documents-connector field becomes a **picker** of the organisation's
`documents` connectors of the right type (with a link to declare one when the list is empty). The API
keeps refusing a wrong name, with a message that names the cause (case, wrong kind, the list of
existing connectors) and now checks the connector **type** against the source kind.

**Decision, part (b).** *Connector secrets are write-only values, sealed in the database.*
- A secret field accepts a typed value (default) or a reference (advanced). A typed value goes to a
  `SecretStore` seam and leaves a **derived reference** in the connector (`store:…`); a user may never
  write a `store:` reference by hand (otherwise one tenant could read another's secret).
- Envelope encryption: a random data key per value (AES-256-GCM, AAD binds organisation, name and
  version), wrapped under a key-encryption key from the deployment; keys rotate by re-wrapping, never
  by re-reading the values. No plaintext, no hash. No key configured means writes answer 409 and
  references fail visibly.
- Values are never returned; the console shows "set, last rotated" and a replace control.
- External managers stay reference schemes through the existing resolver seam; writing to one from the
  console is rejected (it would give a tenant-facing process a platform credential with write rights).
- **Security fix, first.** An `env:` reference resolves only names matching an operator-set pattern
  (default `CONNECTOR_*`), never the platform's own variables; writing any `env:` reference needs the
  organisation admin.

**Rejected.** Writing to the operator's secret manager from the console; a hash or fingerprint of the
value (leaks low-entropy secrets); keeping `env:` as the only path.

**Stories.** `S39-06a` the picker and better messages; `S39-06b` the `env:` allowlist (can merge with
6a); `S39-06c` `contract(connectors)` the sealed store; `S39-06d` web secret fields; `S39-06e` the
operator's deployment PR carrying the key.

**ADR.** **0058 — Connector secrets are write-only values, sealed in the database.**

**Left to the operator.** Generate the key-encryption key and put it in the deployment's secret store
*before* merging the deployment PR (otherwise the pod receives `<no value>`); register the identity
application for SharePoint; read-only check of the existing connectors and removal of half-created ones.

### Item 7 — A gateway-agnostic model catalogue

**Decision.** Complete the existing protocol instead of renaming it.
- `GatewayAdapter` gains declared **capabilities** (`list_models`, `virtual_keys`, `hard_budget`,
  `spend_readback`, `teams`, `pricing`), checked by a conformance test, and a `test()` call. A new
  `openai-compatible` adapter lists models from `GET /models` and says plainly that with it **budgets
  are enforced by Choregos only** (reservation, turns, minutes); no hard cap at the source, no measured
  cost.
- An **organisation model catalogue**: per model, enabled or not, allowed stage roles, usages (agent,
  embed, distill, eval), price override, notes; filled from the gateway by a sync and by manual entries.
  Tiers (cheap … local) per organisation sit between project profiles and platform profiles.
- Two modes: `open` (today's behaviour, the default) and `curated` (only enabled models; newly
  discovered ones arrive disabled). Switching to curated shows first what would be refused.
- Enforced where it matters, always non-retryable and naming the model: the resolver, agent
  publication, project profile edits, and the API's own uses (embeddings, distillation). The gateway
  side is unchanged: a run's key already names the resolved model only.
- `/platform/models` uses the configured gateway, not LiteLLM.

**Rejected.** Renaming to `LlmGateway` and `litellm_model` to `model` (a contract break for no
behaviour: an alias and the documentation suffice); enforcing only at the gateway (impossible without
virtual keys, invisible in the console); storing the catalogue in the gateway's routing file; making
Choregos a metering proxy; stage roles confused with RBAC roles. Portkey, OpenRouter, Kong AI Gateway,
Envoy AI Gateway, Cloudflare AI Gateway and Azure API Management are named as future adapters.

**Stories.** `S39-07a` capabilities, the OpenAI-compatible adapter, no hard-coded LiteLLM; `S39-07b`
`contract(api)` catalogue, tiers, modes, enforcement; `S39-07c` the Models page of the administration.

**ADR.** **0060 — A gateway-agnostic model catalogue.**

**Left to the operator.** Nothing required; after release, sync from the gateway, review, optionally
switch to curated.

### Item 8 — External agents such as Rovo

**What Rovo exposes.** (1) An MCP server: *tools*, not an agent, authenticated by OAuth or by an API
token sent as Basic. (2) An **A2A gateway**: the only way to invoke Rovo itself; one agent with two
skills (work in Jira, work in Confluence), OAuth authorisation code with PKCE and dynamic client
registration only, so everything runs **as the authorising user**; no service-account flow; no push
notifications; synchronous calls are cut at about 30 s. Custom agents built in Rovo's studio are not
individually addressable.

**Decision, two paths.**
- *Path 1, tools through MCP:* the MCP client learns Basic authentication, so an organisation `mcp`
  connector can reach Rovo's MCP server with a scoped service-account token, under the platform's
  per-operation policy and approvals.
- *Path 2, remote agents over A2A:* a new agent kind `remote`, invoked **by** Choregos as an ordinary
  workflow step (the DSL does not change: no replay), running in the **runner pod** (`_execute_remote`
  next to the job path), so admission, events, gates and the pod's egress policy all apply. The card is
  fetched and pinned (digest) at publication; drift refuses the run. Results map to the summary,
  outputs and facts (declared, not measured); the transition's gates apply unchanged. Cost is
  **declared**, booked as `external`, reserved at admission, shown apart and labelled unmeasured when
  undeclared. Credentials are an organisation object (OAuth with a rotating refresh token kept in the
  sealed store; only a short-lived access token reaches the run's secret). An endpoint host must be in
  the project's allowed domains.
- `input-required` fails the run with the question visible in phase 1; mapping it to the human question
  and resuming on the same context is phase 2.

**Rejected.** An orchestrator activity calling A2A (it would hold user tokens in the orchestrator,
bypass the run lifecycle, and need new workflow code); the A2A SDK as a hard dependency (four client
calls do not justify its weight); a webhook runtime (no standard task lifecycle). Choregos *as* a Rovo
remote agent inside Jira (a Forge app and an A2A server) is a follow-up, not in S39.

**Stories.** `S39-08a` Basic authentication for MCP; `S39-08b` `contract(api)` remote agents,
credentials, runs (depends on 06c); `S39-08c` the console: register from a card, connect, run.

**ADR.** **0062 — Remote agents over A2A.** Amends `docs/positioning.md` ("A2A: client surface").

**Left to the operator.** Allow A2A and API-token access in the Atlassian administration; a dedicated
Atlassian account licensed for Rovo; the OAuth consent as that account; egress allow-list entries for
the three Atlassian hosts; the project's allowed domains.

### Item 9 — Governance of agents

**Decision.** Four scopes in one slug namespace (so the DSL and the replay do not change):
`platform` (installed from the built-in catalogue, curated), `org`, `project` (one project, runs only
there), `personal` (one user).
- One server-side function decides every action; it returns a reason, and the agent DTO carries what
  the caller *can* do so the console disables buttons with the server's own sentence.
- Common agents are modifiable by an organisation admin only ("diverges from the catalogue: prefer a
  fork"). A project owner may create and manage project agents; any developer may create personal ones.
- **Personal agents never run in a project's workflow** (a shared process must not depend on one
  person's private object): they run in trials, and are promoted or forked to reach a workflow.
  Enforced at pin, at workflow publication and at run time, with the existing non-retryable error.
- **Fork** copies a version byte for byte into a new agent of the target scope, records its origin and
  never touches the source. A fork shows when upstream moved ("behind") and offers a re-base **on
  click only**, never automatically.
- Migration: catalogue-installed agents become `platform`, the rest `org`; nothing changes hands.

**Rejected.** Namespaced slugs (a DSL contract change touching every resolver and replay); per-agent
ACLs (can sit on the decision function later); personal agents in shared workflows; forks that follow
upstream; a new `maintainer` role (`project_owner` already is one).

**Stories.** `S39-09a` `contract(api)` scopes, project and personal agents, forks, migration;
`S39-09b` badges, scope filter and forks in the console.

**ADR.** **0061 — Agent ownership scopes and forks.** Amends 0033 §1-2 and 0040 §4.

**Left to the operator.** After release, decide which organisation agents become project agents.

### Item 10 — A catalogue of MCP servers

**Decision.** A curated, versioned catalogue file in the image (no network at run time), **generated**
by a script from a reviewed seed list and recorded sources, never auto-enabled. An entry is "available
to install"; installing creates an ordinary organisation `mcp` connector (admin only, secret through
the sealed store of item 6, tools born closed). Entries carry publisher, `official` (derived from
registry namespace or repository owner against a vendor map, never by hand), licence, transport, auth,
egress hosts, categories, and a computed `installable | needs_oauth | needs_hosting`.
- The generator replays recorded HTTP (byte-deterministic) and applies exclusion rules in code, each
  reported with its reason: inactive or archived, ephemeral-tunnel and relay hosts, aggregators,
  desktop and arbitrary code execution, anti-bot, wallets and payments, unlicensed stdio, non-TLS.
- v1 installs `none`, `bearer` and a named header. OAuth-only vendors are **listed, not installable**
  until the OAuth connector of item 8 lands. Stdio servers are `needs_hosting`: running third-party
  code is a supply-chain decision for the operator (an optional chart feature follows).
- The console says per entry whether the deployment declares the host reachable, instead of a silent
  timeout; an operator may add its own site catalogue.

**Rejected.** Mirroring the official registry (a verified phone book of tens of thousands of entries,
many unsafe); ranking by stars alone (non-MCP repositories dominate); a generic stdio-to-HTTP bridge;
auto-discovery (ADR 0014: a directory that updates itself is not an access control).

**Stories.** `S39-10a` `contract(api)`; `10b` generator and catalogue file; `10c` browse and install
API; `10d` console; `10e` (optional, later) chart-hosted MCP servers.

**ADR.** **0065 — Catalogues of MCP servers and skills** (shared with item 12).

**Left to the operator.** Egress entries per enabled server; the credentials; OAuth app registrations
for vendors that need them; the operator's own servers.

### Item 11 — English names

**Decision.** Everything user-visible is already English except **one template** and one engine word.
Joiners-leavers 2.0 gets English agent and skill slugs, connector names, state, actor, input and output
ids, transition ids, action kinds, enum values and ontology names; the engine effect `verifier` with
`motif` becomes `check` with `reason`, the old names kept as aliases. The guard now scans `templates/`
identifiers. A **tool re-publishes a tenant's French names** (dry run first, then apply) for data created
before ADR 0039; trial projects whose slugs cannot be renamed are deleted or keep English display names.

**Rejected.** Renaming in place (immutable versions, pinned items); a silent migration (in-flight items
sit on French states).

**Stories.** `S39-11a` the `check` effect; `11b` joiners-leavers 2.0 and the scanner; `11c` the
tenant-renaming tool. Follows ADR 0046; no new ADR.

**Left to the operator.** Mint an admin token, run the tool dry then applied, decide the trial projects,
retire the French agents and connectors after the open items close.

### Item 12 — A catalogue of skills

**Decision.** The same shape as item 10: a catalogue file generated from **pinned commits**, installed
in one click through the existing door and gate, never installed by default, never followed
automatically.
- Inclusion rules in the generator: an open licence only (proprietary, source-available and absent
  licences are excluded; they stay importable by hand where a person decides); the gate must not refuse
  it as is; the publisher on an allowlist **and** at least 1 000 stars or a vendor organisation (which
  defeats the cloned repositories with inflated installs); no skills that only make sense in another
  tool's plumbing; one entry per name.
- Two deliveries: **bundled** (a starter set of ~25 permissive, low or medium-risk skills vendored in
  the image with licence files and provenance, no network needed) and **git** (everything else; the
  install calls the existing import at the pinned commit).
- The gate runs again at install; the precomputed risk is informative. High risk still waits for a
  second administrator. A newer pin shows as "update" and installs only when a person clicks: two
  humans between upstream and an organisation.

**Rejected.** Seeding every organisation with installed skills; proxying a popularity site (gameable,
no licence data); bundling everything (copyleft content in an Apache-2.0 image); recommending skills the
operator may not be licensed to use.

**Stories.** `S39-12a` `contract(api)` (after 10a); `12b` generator and file; `12c` install; `12d`
console (after 10d).

**ADR.** **0065** (with item 10).

**Left to the operator.** Egress for the git host; a decision on proprietary document skills (import
by hand if their agreement covers it); installing the starter set after release.

### Item 13 — Agents and artifacts on the workflow pages

**Decision.** It is a gap, not a design choice. The process model carries, per step: the registry
agent (slug and version) as well as the actor key, the role, the model, the human group and its SLA,
the job command, the declared inputs and outputs and their types, and which step produces what another
step consumes. The console shows it: the Process tab names the agent with a link, lists inputs and
outputs; the Map's boxes show them and the side panel describes before it edits; a job step gets its
own icon. The `ProcessStep` schema is re-aligned with what is served.

**Rejected.** A separate "artifacts" page (the question is asked from the workflow); inferring
outputs for steps that declare none (the implement step's code change is implicit: the page says so).

**Stories.** `S39-13a` `contract(api)`; `S39-13b` web.

### Item 14 — Project knowledge from the project

**Decision.**
- Every project gets a **Knowledge** section: its own bases and, read-only, those shared with every
  project. **Creating from there scopes the base to the project by construction** (no picker); the base
  opens inside the project.
- `/knowledge` stays the organisation's registry with scope filters, a clearer "Used by" column and a
  checkbox list of projects instead of free text.
- **Project owners curate their project's bases**: a base created from a project is *owned* by it (a
  new nullable column); its owners may create, upload, add and sync sources, patch and distil it; only
  an organisation admin may widen its scope, which clears the ownership.

**Rejected.** A singular `project` scope (duplicates `projects: [x]` and touches every consumer);
inferring ownership from a one-project scope (narrowing an organisation base would silently hand it
over); web-only (kept as PR 1, but governance needs PR 2).

**Stories.** `S39-14` PR 1 web; PR 2 `contract(knowledge)` ownership, migration, RBAC tests.

**ADR.** Amends **0051 (knowledge bases)** with "a project-owned base".

### Item 15 — A documentation step

**Decision.** In the default delivery workflow, a `t-document` transition between test and review,
run by the documentation agent with role `document` (not `implement`, which would skew first-time-right
metrics and the commit prefix), producing `docs_report`, gated by scope, no secrets and a **new gate
`docs_updated`**: documentation under the declared paths changed, or the change touched nothing
documentable. The reviewers then read the docs as part of the diff, release notes consume the report,
and a review that asks for changes re-runs the writer. The role is added to the roles that work in the
repository. The governed template is not changed here.

**Rejected.** Placing the step after the security review (nobody but the maintainer would read it, and
a review loop would not re-run it); reusing `markdown_sections` under a misleading name.

**Stories.** `S39-15`: one PR, no contract change (gate names are not in the contract).

**Left to the operator.** After release, publish v2 of the workflow on the project (it is not
automatic: a project receives its template once), migrate in-flight items on request, update the
specification agent from the catalogue.

### Item 16 — Create work items from the board

**Decision.** A person creates a work item from every board. With an external tracker, Choregos creates
the **issue through the project's tracker adapter inside the same creation path, then records the work
item under the issue's key**: one source of truth, the mirror coherent as if the webhook had brought it.
The MCP door gets the same behaviour. The issue is created **without the dispatch label**, so the
webhook cannot race the transaction and create a second item; an orphan issue (database failure after
creation) is a plain issue a person can label, and the error says so. Adapter failures answer 502 and
create nothing here. Permissions are unchanged. The console shows "New work item" on every board, in
the drawer, says which tracker will receive it, and treats "no tracker row" as internal.

**Rejected.** Keeping the 409 and linking to the tracker's form (loses creation inputs, budget and
workflow choice); a Choregos-only item on an external project (two sources of truth); creating the
issue with the dispatch label and letting the webhook create the item (asynchronous, loses fields).

**Stories.** `S39-16a` `contract(work-items)`; `S39-16b` web and Playwright.

**ADR.** **0059 — A work item filed in Choregos is born in its tracker.**

**Left to the operator.** Confirm the tracker integration may write issues; check the first creation
on the instance.

### Item 17 — Agents written in code

**Decision.** *A code agent is an ACP agent shipped in an operator-named image built from the runner
image, launched by a generic `code` backend, written with a small SDK that hides ACP.* ACP keeps every
guarantee (permissions, journal, turn limits, cancel, conformance).
- `choregos-agent-sdk`: a decorated async function with a context (task, fields, inputs, an
  OpenAI-compatible client on the run key, MCP tools, outputs) returning a typed result. **Tool calls go
  through the runner's permission path**, which is why the SDK, not user code, makes them.
- `AgentSpec.runtime` becomes a discriminated union (`acp` by default, `code`; item 8 adds `a2a`).
  An image is a **name** in the operator's map, digest-pinned, never a free reference (same rule as job
  images); the chart renders both maps; a reference without a digest is refused at startup in
  production.
- Conformance for third-party agents; two examples.
- **Fix first**: the `agent_sandbox` executor refuses a per-step image other than its warm pool's,
  instead of silently running the runner image.

**Rejected.** A job-style contract with a gateway key (loses permission gating and turn accounting;
the `job` actor already serves model-free code); installing code at run start (mutable references and
transitive dependencies).

**Stories.** `S39-17a` executor fix; `17b` `contract(schemas)`; `17c` SDK, examples, conformance;
`17d` the builder.

**ADR.** **0063 — Agents written in code.**

**Left to the operator.** Publish the SDK and contracts packages to the package index; build a first
agent image in the operator's registry and list it in the deployment values.

### Item 18 — A knowledge base about the operator

**Decision.** The product work is generic; the content is the operator's.
- Fix the crawler: a source that suddenly yields zero pages, or whose start URL redirects, **never
  deletes** its documents; path and language exclusions; page names that stay unambiguous across
  languages.
- A git source reads a **private** repository through a `documents/git` connector (a credential from
  the sealed store).
- A declarative manifest applied by `choregos knowledge apply` (idempotent, dry-run, prune): the base,
  its sources by name, uploads, an eval set. Knowledge becomes reproducible, not clicks.
- The base itself is a manifest plus about a dozen curated pages **written from the operator's public
  pages only**, each fact citing its URL, plus an eval set of about twelve questions; it lives in the
  operator's deployment repository. An optional second base for internal platform guides is restricted
  to a group. Nothing is applied before the operator reviews the corpus.

**Rejected.** Scraping everything (the cap of 500 documents, four languages, ambiguous citations);
indexing internal business folders (they may name prospects and clients); clicks instead of a manifest.

**Stories.** `S39-18a` web source fixes; `18b` private git source; `18c` the CLI; `18d` the manifest and
corpus in the operator's repository.

**Left to the operator.** An administrator token to run the apply (or run it by hand); the credential for
private repositories; validating the curated corpus; deciding whether and for whom the internal base
exists.

### Item 19 — Refreshing a knowledge base on a schedule

**Decision.** Keep the existing per-source Temporal loop unchanged and move the "when" into the source
row and the activity, so cron, pause and "next sync" need **no workflow change** (no patched id, the
archived history still replays). New fields: `refresh_mode` (`interval | cron | manual`),
`refresh_cron`, `refresh_timezone`, `next_sync_at`, `sync_requested_at`. The activity decides whether a
pass is due and how long to sleep; a pass that is not due touches nothing (which also stops a worker
restart from resyncing at an off-cron moment). Editing the refresh takes effect at once; a base-level
"refresh all sources now" and "apply this cadence to all sources" exist as conveniences, **not** as a
second stored setting (a base is the union of its sources, each with its natural cadence).

**Rejected.** A per-base setting; a new workflow version; sharing the cron matcher of scheduled work
items (#510) by editing it (the story must not conflict with it).

**Stories.** `S39-19`: one `contract(knowledge)` PR.

### Item 20 — A Confluence space or sub-space

**Decision.** A connector type `documents/confluence` (organisation connector: site URL, account email,
`basic` or `scoped` token, the token typed once into the sealed store) and a knowledge source kind
`confluence` (space key, optional root page for a sub-tree, include-root, optional attachments in the
supported formats, optional label filter). It rides the existing document-source protocol: version
skipping, deletions via full listings guarded against false deletions, HTML converted by the sandboxed
converter, periodic sync from item 19. The connector interface is generalised first (a connector opens a
source from its configuration; the API's SharePoint-only check becomes a table of allowed types).
OAuth (3LO) is deferred: it needs a registered app and a rotating refresh token.

**Rejected.** Using the Jira tracker connector (different object, different permissions); a personal
token (a knowledge base wants one stable identity: a dedicated service account with read on the chosen
spaces).

**Stories.** `S39-20a` `refactor(knowledge)` connector interface; `S39-20b` `contract(knowledge)` the
Confluence connector and source; `S39-20c` (optional) OAuth.

**ADR.** Amends **0051** (new source kind) together with item 14.

**Left to the operator.** A service account with read on the spaces, an API token (classic, or scoped
with the four read scopes), declaring the connector, and the OAuth app for 20c.
