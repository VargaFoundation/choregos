# Trial, element 9 - local start: results of 2026-10-04

**Question**: does the trial's stack start with `docker compose up` on a laptop in
**10 minutes at most and 6 GB at most**? And does the IT4IT slice (elements 1 to 6) hold against this
running stack, and not only in the tests?

**Answer: yes to both, on a development machine with cached images.** The time on a new
workstation depends on the download (about 1.5 GB of images). And the running stack found a
defect in the core, invisible to the tests: a request's transaction was committed **after** the
response was sent.

## The integrated stack (`compose.yaml`, `run.sh`)

- **PostgreSQL** (`postgres:16-alpine`) with a **non-superuser application role**
  (`initdb/`): migrations and the API run under this role, hence under forced RLS;
- **migrations** by `python -m choregos_api.migrate`, the chart's Job command: the core, then
  the extension's `ontology` branch;
- **API** (uvicorn) and **orchestrator** (Temporal worker), images built from
  `docker/api.Dockerfile`, plus a 238-byte layer that declares the extension as
  `pip install` would (`extension.Dockerfile`);
- **Temporal** (`auto-setup:1.26.2`);
- the **lakehouse** of element 7 (Lakekeeper, its database, and RustFS in place of MinIO, Q22), included
  as is;
- the run-token key pair, generated by `run.sh` and shared by the API, the orchestrator
  and the scenery.

## The defect found: the `commit` after the response

First run: the sign-in succeeds, the next request answers **401 "stale session"**.
FastAPI closes `yield` dependencies **after** sending the response by default; `get_db` committed
its transaction there. The client received its redirect, then the database wrote the user: a fast
request arrived before. Measured on the stack: **6 new sign-ins out of 10 fail** with no wait,
none with half a second.

The most serious consequence is not the race: a `commit` that fails afterwards leaves the client
a success response for a lost write. The tests did not see it, because
`ASGITransport` waits for the application to finish before returning the response.

Fix in the branch: `Depends(get_db, scope="function")`, which commits the transaction before
sending. The test `apps/api/tests/test_commit_avant_la_reponse.py` calls the ASGI application
directly and checks the order of events; without the fix, it fails. A `finding` issue
opened for the main line.

## Replayed on 2026-10-06, after S20-08: the orchestrator runs the ontology

Since S20-08, an ontology proposal is a core action: the decision answers BEFORE
any effect, and it is the `ActionWorkflow`, in the orchestrator, that opens the PR then waits for the proof.
The integrated stack proves it outside the tests: the nine steps pass, the PR opened by the worker after
the re-authenticated approval, the proof settled by the collector's re-run - under forced RLS,
`actions` included (the `action_proposals` table no longer exists, `onto0003`). Start-up 17 s, 664 MiB at
rest (images cached).

The scenario had to follow: it now waits for the state it reads (the decision returns `approved`, the action
succeeds afterwards; the re-run only settles a proof REQUESTED before it), reads
`auth_age_seconds` instead of `auth_time`, and counts 14 generated tools. And the stack did not activate the
extension, shipped inactive since 0.13.0: `CHOREGOS_ONTOLOGY_TRIAL=1` in `compose.yaml` - the trial
had been broken since, with nothing saying so.

## What element 9 does not prove

- **The time on a new workstation**: about 1.6 GB to download, that is 2 to 3 minutes at 100 Mbit/s and
  twice that at 50 Mbit/s, under the 10-minute goal; not measured on a real slow connection. The
  MinIO blocker is lifted: RustFS replaces it (element 7, section Q22), and the stack no longer depends on
  any cached image.
- **Local mode without a development login**: authentication goes through `?as=`; the spec's local
  mode (password, ADR 0011) does not exist in the core.
- **The agent, the collector and the SCM**: the scenario writes the agent's calls, posts the collector's
  reports, and the PR opens on the core's fake SCM, inside the API process.
