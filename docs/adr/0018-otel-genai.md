# 0018 — OpenTelemetry GenAI conventions from the runner and the gateway

- **Status**: proposed, 2026-09-25 — partially implemented on 2026-10-22 (S40-20: points 1 and 4;
  S40-20b: point 2, the collector's pipeline and the dashboard), point 3 on 2026-10-23 (S40-20c, the
  drift job; see *Implementation*)
- **Concerns**: the runner, LiteLLM, the API and orchestrator logging, `infra/bootstrap/otel-collector.yaml`

## Context

An OpenTelemetry collector is installed by Argo CD in wave 2 (`monitoring` namespace,
daemonset mode). Nothing sends it a span. Since P0-4 the API and the orchestrator expose
Prometheus metrics and log with `structlog` (request id, `project`, `work_item`, `run_id`,
`stage`), but a run is still read as a list of journal rows, not as a trace.

The OTel **GenAI semantic conventions** (`gen_ai.*`, status *Development* in 2026) name the
spans we need: `invoke_agent`, `execute_tool`, and the client spans for model calls with
`gen_ai.usage.input_tokens` / `output_tokens` and `gen_ai.request.model`. LiteLLM emits the
client spans natively through its OTel callback.

## Decision

1. **One trace per run.** The orchestrator opens a span `invoke_workflow` per stage attempt,
   propagates the context to the Job through the environment (`TRACEPARENT`), and the runner
   opens `invoke_agent` for the ACP session. Every MCP call through the sidecar becomes an
   `execute_tool` span (name, duration, `is_error`, the catalogue tool's provider, never its
   arguments).
2. **Model calls are the gateway's spans**, not the runner's. LiteLLM's OTel callback is
   enabled in the embedded chart with the run id as `gen_ai.conversation.id`; the runner
   never sees the request and never invents token counts.
3. **The ledger stays the truth for money** (ADR 0004). Traces carry `gen_ai.usage.*` for
   reading, and a nightly job compares the sum of a run's trace usage with its ledger rows;
   a drift is a finding on the platform, not a correction of the ledger.
4. **Correlation keys are the structlog keys.** `run_id`, `work_item`, `project`, `stage`
   go on every span as attributes, so a log line and a span meet on the same values.

## Conditions

- The conventions are in Development: attribute names may change. The semconv version is
  pinned in one module (`choregos_core.telemetry`), and only that module knows the names.
- No gate reads a span. A guarantee is a mechanism on data the platform holds (ADR 0010);
  a trace can be sampled, dropped or late.
- The agent's prompt and the tool arguments are **not** recorded on spans: the journal already
  holds what the evidence pack needs (ADR 0015), and the collector's retention is not ours to
  audit.

## Consequences

- A run reads as a tree: stage → agent session → tools and model calls, with durations. The
  "why did this stage take 40 minutes" question gets an answer from Jaeger or Tempo instead
  of a psql query on the bench.
- The dashboards that P0-4 pruned back to exposed metrics can gain RED panels per stage from
  span metrics, generated by the collector — still no orphan panel.

## Alternatives discarded

- **Writing our own trace format into `run_events`**: the journal is the durable record and
  stays; duplicating it as a proprietary trace gives nothing a collector does not.
- **Instrumenting the agent itself** (Claude Code, Codex, Gemini CLI): the agents are
  black boxes by design (ADR 0002, BYO agent); we measure their edges, not their insides.

## Implementation (S40-20, 2026-10-22)

- `choregos_core.telemetry` holds the names (semantic conventions 0.66b0, schema 1.44.0; a test
  compares each name with the package) and the helpers; the SDK and the OTLP/HTTP exporter are
  pinned exactly in `choregos-core`. Tracing is off unless `OTEL_EXPORTER_OTLP_ENDPOINT` (or its
  `_TRACES_` form) is set; the global tracer provider is left to the libraries that have one.
- **The context does not travel in a `TRACEPARENT` variable** but in `StageInput.trace_parent`,
  which the contract already had: the warm-sandbox and Tekton paths do not build a pod environment
  per run, the `StageInput` reaches every path. The trace id and the stage span id are **derived
  from the run id** (SHA-256), so the API's tool route attaches its spans to the run's trace from
  the run id in its path, with no lookup and no state.
- `invoke_workflow <stage>` is opened by the `await_run` activity and lasts as long as the wait;
  `invoke_agent <backend>` wraps the runner's `execute`; `execute_tool <tool>` wraps the API's tool
  route (catalogue, plugin, broker, `web_fetch`, `web_search`), so tools are traced where the platform
  serves them rather than in the runner's tool server. `is_error` is the span's error status with
  `error.type` (the HTTP status of the call), the conventions' form of it.
- Not done yet: the nightly drift job (point 3). A Temporal retry of `await_run` emits a second root span with the same
  id; the tools the runner's own tool server answers without the API (`report_finding`, `ask_human`)
  have no span.

## Implementation (S40-20b, 2026-10-22)

- **Point 2 is a callback of ours, not LiteLLM's `otel` one.** LiteLLM's callback starts a trace of
  its own unless the request carries a `traceparent` header, which an agent never sends, and it
  records the messages unless told not to. `choregos_core.llm_spans` (stdlib and the OpenTelemetry
  SDK only: LiteLLM's image has no Choregos package) reads the run id from the **key's** metadata
  (`user_api_key_metadata`, written by `mint_run_key`, set by the proxy from the key on every
  request; the request's own `metadata` is ignored), derives the run's trace id and stage span id
  as `telemetry.run_trace_ids` does, and emits `chat <model>` (or `embeddings`, `text_completion`)
  as a CLIENT child of the stage span: provider, requested and answering model, the provider's
  token counts (none on a failed call), `error.type` and an error status on a failure, the run's
  correlation keys (`stage` is the key's `role`). A key that names no run gets no span. The chart
  ships a byte-identical copy (`charts/choregos/charts/litellm/files/choregos_llm_spans.py`, a test
  keeps them equal) loaded through `litellm_settings.callbacks`.
- **One value turns tracing on**: `global.tracing.otlpEndpoint` becomes `OTEL_EXPORTER_OTLP_ENDPOINT`
  on the API, each worker, the migration Job and the embedded gateway. The agent pods do not get it,
  and since S40-20d their network policy does not open the collector either (#946): their only way
  out is the run's egress proxy, so the runner's `invoke_agent` span is not exported.
- **The collector**: the bootstrap values were `mode: daemonset` alone, which the chart refuses to
  render (`image.repository` must be set) and which exported nowhere. It is now a Deployment of the
  contrib image behind `otel-collector.monitoring.svc` (OTLP on 4317/4318), sending every span to
  Tempo and to a `spanmetrics` connector whose dimensions are bounded (operation, model, provider,
  project, stage, `error.type`; never a run id). Its Prometheus exporter is scraped through a
  ServiceMonitor.
- **The dashboard** `traces.json`: rate, errors and p95 duration per stage, model and tool, from the
  span metrics. A test refuses a panel that reads a label the connector does not produce, and the
  live test (`tests/live/test_otel_collector_live.py`, LiteLLM + the rendered collector config +
  Tempo in Docker) refuses one that the collector never actually writes.

## Implementation (S40-20c, 2026-10-23)

- **The drift job** (point 3) is `python -m choregos_api.trace_drift`, run nightly by the CronJob
  `choregos-trace-drift` when `global.tracing.tempoUrl` names Tempo's query address. For each run
  whose spend was collected in the window, it sums the ledger's `model` rows and the
  `gen_ai.usage.input_tokens` / `output_tokens` of the gateway's spans in the run's trace (read by
  the derived trace id), and compares them within a tolerance (1 % of the ledger's figure, at least
  one token). A drift becomes a **platform** audit line `trace.drift` (`org_id` NULL, so only a
  platform session reads it), once per run whatever the number of nights that see it; the ledger is
  never touched. A run whose trace has no gateway usage is `missing`, counted and not recorded: a
  trace can be sampled, dropped or late. A remote agent's `external` line is not compared.
- Only spans whose resource `service.name` is `choregos-gateway` count. That name is a claim, not
  an identity: any process that reaches the collector can write it. Until S40-20d the runner pods
  could, their network policy opening port 4318 in `monitoring` (#946); it is closed, and a chart
  test refuses any runner policy that opens the collector. The platform's own pods can still write
  that name. A forged span can raise a false drift; it cannot change the ledger.
- **Not decided**: relaying the runner's `invoke_agent` span through the API (the API stamping the
  run's ids and refusing usage attributes) instead of exporting it from agent code.
