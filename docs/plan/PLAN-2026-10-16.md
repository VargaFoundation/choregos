# Plan — 2026-10-16: governed network access, an agent's release lifecycle, a project that can be configured, catalogues with rights

Source: the product owner's request of 2026-10-16 (12 items). Each item was checked against the code
of the integration branch of the day (`integration/s39-batch-3` for most items, batch 4 where an item
builds on the MCP and skills catalogues) and, where it touches the operator's running instance, against
what that instance actually runs (read-only). Stream number: **S40**; story ids `S40-NN` where `NN` is
the item number below. A detailed plan per item (design, steps, tests, overlaps, implementation briefs)
was written for each story; this page is the summary that stays in the public repository.

Status words: **exists** (in the code), **missing**, **broken** (exists and is wrong).

Scope note: this repository is public. Several items arise from one operator's deployment (a dev
instance, an enterprise edition, a platform team that owns the cluster and its network rules). They are
described here in generic terms ("the operator's dev instance", "the operator's deployment repository",
"the operator's platform repository"). What belongs to the operator's own infrastructure lives in the
operator's repositories, not here.

Dependencies on the previous stream: S40 builds on S39 contracts that are not merged into `main` yet

## 1. Decisions, item by item

### Item 1 — Network access policies, for agents and for the organisation

**Decision.** *Network access is bounded by the organisation, narrowed by the project and the agent, and
enforced per run by an egress proxy.* One model, three scopes, **intersection only**: the organisation's
ceiling gains a network section (allowed set, a deny list that always wins, rate caps, whether built-in web
tools are allowed, a contact for the User-Agent); the project's allowlist must lie within it; an agent
version declares its own list (`null` = the project's, `[]` = no internet, a list = only these), which is
validated at publication and at admission and can only narrow. The run's effective allow list is the
intersection plus the hosts its own repository needs; the deny list is the union. One host-pattern grammar
(`example.com`, `*.example.com`, `*`; **no IP literals**) is implemented once and used by the API, the
orchestrator, the runner and the proxy.

Enforcement is layered and **each layer says how strong it is** (ADR and security docs):
- a **per-release egress proxy** that identifies the run (run id and token), applies the effective policy,
  refuses IP literals and private addresses, limits connection rate per host, per run and per organisation,
  and journals decisions. It holds no secret and no database access, and a changed ceiling applies within
  a minute. It is a wall for host, port and connection rate where the cluster network forces traffic
  through it;
- the **platform's own calls** (tool broker, knowledge crawls, git skill import, catalogue installs, remote
  agent cards) obey the organisation's policy at declaration and at call, with an identifying User-Agent,
  robots.txt and per-host politeness: a wall, because the API makes the call;
- a **governed `web_fetch` tool**: GET and HEAD only, the run's allowlist, robots.txt, size cap, redirects
  re-checked: the one place where method and path rules can hold;
- the runner's guardrails and the backend settings that turn built-in web tools off: **advisory** (a
  safety net with a useful message; the agent shares the pod);
- model-provider server-side tools: advisory by nature, said so in the docs.

An **audit table** records, per run, layer, host and decision (counts, bytes, first and last seen), readable
by an administrator, and the first denial per run and host lands on the work item's timeline. The console
gets the organisation's network policy, the effective project network, the agent's network in the builder,
and a network-activity view. The runner presets gain the hosts package installs and GitHub downloads need;
`deny_by_default` now produces a warning instead of being silently ignored.

**Rejected.** Per-agent Kubernetes or Cilium policies by pod label (warm sandboxes exist before their run;
tenants may not create network policies; not portable). Keeping the current proxy and rendering a union per
project (no run identity, no rates, no audit). A proxy built on an external-ACL helper (harder to test with
fakes than a small asynchronous proxy). **TLS interception** to see paths (a CA trusted by every tool in the
runner image, and a holder of all cleartext). A separate "network policy" object with its own CRUD (the
ceiling, policy and agent spec already carry publication, versioning, audit and clamps).

**PRs.** Contract and core grammar #618 (ADR **0070**); runner receives and holds its effective network
#621; per-run egress proxy #633; platform-side calls obey the organisation policy #637; console #635;
governed `web_fetch` #648; deployment PR drafted in the operator's deployment repository.
Findings: the broker check on declared connectors (#625).

**Left to the operator.** Allow the proxy's outbound hosts in the operator's platform network rules, then
remove the runners' direct host rules so the proxy is no longer bypassable; set the organisation's ceiling
(deny list, per-host rate, a monitored User-Agent contact); merge the deployment PR after that; an option
to turn built-in web tools off by default is left as a decision.

### Item 2 — Publishing an agent and its lifecycle: eval, testing, production

**Decision.** *An agent version reaches production through channels.* A **revision** is an immutable
version row, as today. An agent has two channels, each a pointer to a revision: **production** and
**testing**. "Publish" keeps meaning "save the next revision"; **"release"** means "point a channel at a
revision" (the word "promote" is already used for a change of scope). Each agent carries a release policy
whose `on_publish` is `stable` (**default: today's behaviour**, so nothing changes for anyone who does
nothing), `candidate` or `none`; the console proposes testing-first for organisation and project agents.

- **Eval** is every revision's entry gate: the deterministic suite as today, plus, later, a **live
  evaluation** (the suite's live cases run as capped trials on the real model, scored).
- **Testing** serves the revision to projects that follow testing and to a **deterministic canary share**
  of other work items (a hash of agent and work item, so every stage and retry of one item sees the same
  revision).
- **Production** is the default for every project that does not pin; moving it can require that the
  revision *is* the current candidate, a minimum of real runs, a success rate, a soak time and a minimum live
  score. **Rollback** restores a revision that was previously in production and skips the gates (speed in
  an incident) but keeps rights, a human session and fresh authentication.
- Resolution of a run, first match wins: explicit `agent@N`, fixed project pin, channel pin, project
  follows testing, canary, production. Overrides now **take the minimum**.
- Every move is recorded in a release history (kind, version, previous version, requester, reason, the
  checks as evaluated), which is also the rollback oracle and the lifecycle tab's timeline.
- **Approvals**: an optional request/decide step, by someone with the release right, in a fresh human
  session, neither the requester nor the revision's author (separation of duties). API tokens may save
  revisions and send them to testing without a canary share; production is a person's decision.
- The three latest-version readers are fixed to read the version that ran.
- The enterprise edition registers its organisation-wide fresh-authentication rule on the release gesture
  in its own repository.

**Rejected.** Overloading the agent-level lifecycle (it describes the whole agent, not a version).
Per-project environments for agents (an agent is org-level; projects already pin). Automatic promotion or
rollback on metrics (a person decides; thresholds are gates, not triggers). Shadow runs. A mutable draft
stored server-side (the editor is the draft).

**PRs.** Channels, release, rollback #636 (ADR **0071**); approvals #643; console lifecycle tab #654;
live evaluation #656; one enterprise-edition PR in its own repository.

**Left to the operator.** Cut the release and bump the deployment; check on the dev instance that a
promotion after a long session bounces through the identity provider and comes back; run one live
evaluation on a real model with a small budget; raise the enterprise edition's compatibility ceiling if the
release bumps the minor version. Defaults chosen without asking (change if you disagree): the API default
keeps "publish is release"; step-up 10 minutes; rollback skips gates; no automatic promotion.

### Item 3 — The sandbox runtime is the default of a real deployment; a readable settings page with icons

**Decision.** *The runtime of a real deployment is the agent sandbox.*
- The chart and code default executor becomes `agent_sandbox`; Tekton, the plain Kubernetes job, the
  container-apps and the local Docker executors stay available but are **chosen explicitly**. This is a
  breaking default, documented as such.
- The runner namespace default follows the executor (the release namespace for the sandbox; per-project
  namespaces for the others).
- **The deployment tells the API**: the executor kind and an allowed list move into the shared environment;
  the executors endpoint answers from them; a project cannot select a runtime the deployment does not allow
  (422 naming the allowed ones). The page can no longer claim Tekton on a cluster without it.
- **The operator's presence is checked at render**: the chart fails with a clear message when the sandbox
  operator's API is absent (an escape hatch exists for offline rendering). Tekton-only objects render only
  for Tekton.
- **Steps with their own image** (code agents) are sent by a routing executor to a second, configurable
  executor, so the sandbox default does not strand them.
- The sandbox volume lifetime after a finished claim becomes a configurable, short default (the change that
  fixes the quota exhaustion is a separate, already open PR this item depends on).
- **The page** becomes sections with a navigation rail, one **card per connector** with the human title
  first and the kind as a muted tag, readable reasons, and an **icon per connector type**: brand marks from
  an open-licence icon set (the console's own icon set has none), and a generic capability icon where no
  brand mark exists. Fixture and test guard the icon map.

**Rejected.** Keeping Tekton as default and only fixing the API's environment (absent from the operator's
clusters, and it does not answer the request). Defaulting to the plain job executor (gives up the warm,
credential-free sandbox and suspension across a human question, ADR 0016/0053). Failing the chart
unconditionally without the operator (breaks offline rendering in CI). Per-project sandbox templates (out of
scope; ADR 0053's limit stays).

**PRs.** Runtime default, allowed list, render-time check #620 (ADR **0072**; depends on the open sandbox
volume-lifetime fix #612); settings page and icons #638; custom-image routing executor #646; deployment PR
drafted in the operator's repository. Honest "platform default" claims: see item 5 (#629).

**Left to the operator.** Merge the volume-lifetime fix, then the runtime PR, cut a release; merge the
deployment PR and watch one ticket's volumes return within minutes; install the sandbox operator and the
matching network rule on any other cluster before it can leave the plain job executor.

### Item 4 — Never ask for a GitHub installation id

**Decision.** *GitHub App installations are discovered, not typed.*
- The field disappears from both GitHub connector schemas; the repository becomes a **picker** listing what
  the App can see (a schema `format` any connector can opt into), with "type it instead" for a host the API
  cannot list.
- The platform holds installations server-side (a table filled by polling the App, by the post-install
  redirect, and by webhooks when reachable; discovery never depends on webhooks, since a dev host may be
  private).
- **Install from the console**: a link built from the App's own slug, a setup URL that works as a browser
  redirect on a private network, and a signed `state`.
- **Claiming is the isolation boundary.** A token for `owner/repo` is minted only through an installation
  claimed by the project's organisation. In a single-organisation deployment every installation is claimed
  implicitly; with several organisations a claim needs OAuth proof that the person installing manages that
  installation. The claimed id is injected server-side and never shown or stored in the connector config.
- One public App can serve many companies; a per-organisation App through the manifest flow is deferred.

**Rejected.** Hiding the field under "advanced" (derivable, and a typed value can name someone else's
installation). Webhook-only discovery. Trusting the setup callback's id without OAuth in multi-organisation
(GitHub warns it can be forged). One App per organisation now.

**PRs.** Contract #614; implementation #622 (ADR **0073**, amends 0034 for the GitHub types); console #645
(stacked on the settings page); the deployment part is not done. Finding: the published project schema is
missing the definition-of-done field (#623).

**Left to the operator.** On GitHub: set the App's Setup URL and "redirect on update", set "Any account" if
other companies must install it, subscribe to installation events; before a second organisation exists,
enable OAuth during installation and store the client id and secret in the operator's secret store; merge
and release.

### Item 5 — "CD deployment: Unknown"

**Decision.** The answer is that "Unknown" means *never tested*. Therefore:
- **Saving tests.** After a connector write, a secret set or a secret clear, the API runs the same check as
  *Test* (bounded to 10 s; a timeout is an error) and stores it. A failing test does not refuse the save.
- **States the console shows**: Connected, Failing, Degraded, Not tested yet, a "Demo stand-in" badge for
  demo and fake types, "Provided by the platform", "Not connected". The raw word never reaches the screen.
- **Honest defaults**: only what the deployment provides (runtime, gateway, memory) is claimed as a platform
  default; for the other kinds nothing is, so the getting-started step flips from done to to-do, which is
  the truth. The adapter factory keeps its own defaults, so runtime behaviour is unchanged.
- Titles: "Deployment (CD)" and "CI pipelines", the kind as a muted tag.

**Rejected.** A periodic health check (calls to third parties per project every few minutes; saving plus
*Test now* plus a readiness "tested more than 7 days ago" cover the need). Updating status from adapter
calls during runs (couples every call to a write). Renaming the stored value to `untested` (a free string
other clients read; mapping at display time is enough). No ADR; ADR 0034 gets an amendment.

**PRs.** #629 (finding: #626).

### Item 6 — A project settings page that can configure everything and says whether it is ready

**Decision.**
- **Readiness is computed by the API**: `GET /projects/{id}/readiness` returns items grouped by section
  with a state (done, check, todo, not needed), a detail and a fix (a link and who can do it). It reads
  stored state only (no network call), so it stays fast. It covers provisioning, workflow, one item per
  required connector, connector secrets, the GitHub installation, stale tests, repository and measured
  checks, backend, models, budgets, people and human groups, notifications, tools and first work item. The
  overview reads the same endpoint, and the client-side readiness is deleted.
- **The page gets the missing fields**, each in its own section saved independently through the existing
  project update: general (name, template with "a newer version exists", environments, labels, repository
  and measured checks, definition-of-done facts), agents and models (backend restricted to the deployment's
  allowed ones, model profiles as selects over usable models), notifications, tools (a checkbox per
  catalogue tool), people and knowledge and memory as **links with gaps, not duplicates**, and a danger zone
  (suspend, archive, with confirmation).
- Guardrails stay YAML plus a summary; a structured policy form waits for item 1's shape.

**Rejected.** Keeping readiness client-side (it already diverged from the truth). One page-wide form with a
single Save (larger blast radius). Duplicating Members, Knowledge and Memory inside settings. No ADR.

**PRs.** Contract #624; API #632; console #653. Finding: the published project JSON schema drifts from the
API's model (#623).

### Item 7 — Roles in the administration

**Decision.** One pure function decides the label; the card renders its output. Community edition: one
group with no heading, `platform : org_admin`, `project/<slug> : project_owner` (the organisation slug never
appears). Enterprise edition (multi-organisation): `organisation` for the organisation-level line and one
heading per organisation, shown **once**; "platform" is **not** claimed there because an organisation
administrator administers one tenant, not the instance. While the edition is unknown, the enterprise
wording is used, never "platform" before it is proven. The organisation-level line comes first, projects by
slug; the role stays the identifier, its human label a tooltip.

**Rejected.** A label computed by the API (a contract change for a string). Human role labels instead of
identifiers (the identifiers are what group mapping, the CLI and the docs use). "Platform" in the
enterprise edition (false). Changing the CLI's structured `whoami` table (a script may parse it).

**PRs.** #613 (web only, no ADR). The platform-administrator flag is not carried by `GET /me` and is
recorded as a possible follow-up.

### Item 8 — "Integrations"

**Decision.** The entry and the page title become **"Integrations"** (plural, like Projects, Agents and
Skills; the project scope, the route and the docs already say so), and it moves from Catalogue to the
**Organisation** group, first. The organisation sidebar reads: Work (Projects, Inbox), Catalogue (Agents,
Skills, Knowledge), Organisation (Integrations, Spend, Admin). Card titles inside the page that name the
*object* ("Your AI clients") stay: an AI client is a defined concept.

**Rejected.** Keeping "AI clients"; the singular; moving it into the administration (every member mints
their own client token there); a group of its own for one entry. No ADR.

**PRs.** #615.

### Item 9 — The catalogue: MCP servers and connectors, with rights

**Decision.** *Catalogue rights: who sees, installs, enables and uses an MCP server or a connector.*
- **Navigation**: Catalogue holds Agents, Skills, Knowledge, **MCP servers** and **Connectors**. The MCP
  catalogue page moves out of the administration (the old address redirects); a new connectors page shows
  one card per connector type of the registry, grouped by family, with its icon, whether it is an
  organisation or a project connector, where it is configured and what the caller may do. The
  administration keeps governing instances (secrets, operations, policies, groups).
- **Rights**, decided by **one server function** and carried to the console as `can` plus a reason (the
  ADR 0061 pattern; the console never guesses from roles): any member **sees**; only an organisation
  administrator **installs** an organisation-scope entry or sets availability, operation policy and groups;
  a project owner **configures** project-scope types in their project and **enables** organisation
  connectors for their project; **use** requires the connector enabled for the project, an effective policy
  that is not "forbidden", matching groups, and the agent version selecting it.
- **Availability per organisation connector**: `all_projects` (server default: today's behaviour, so the
  migration changes nothing) or `selected_projects`, with opt-in rows; the console's install and declare
  forms default to "selected projects" because available is not enabled. Switching to selected enables it
  for no project, after confirmation.
- **Use is enforced where a project reaches an organisation connector**: the tool broker and the project
  policy agree through one predicate; listing a project's operations shows only enabled connectors.
- Seeing is not secret: catalogue DTOs carry no secret or configuration.

**Rejected.** Per-operation groups only (an entitlement, not a project's opt-in). Letting project owners
edit the entitlement groups (it is the first lock). Backfilling a row per project and connector.
Hiding entries from non-administrators. Building the connectors page from the type list alone (no
organisation state, no rights).

**PRs.** Contract and routes #655 (ADR **0074**; amends 0034, 0065 and 0014; batch-4 base); MCP servers page
#657; connectors page with icons #658. Egress for an installed MCP server stays with item 1.

### Item 10 — Agent tags

**Decision.** A tag is **agent metadata, not part of a version**: a JSON list on the agent, edited like its
display name and description under the same governance rule, never publishing a version and never changing
a checksum. Shape: a lowercase slug, at most 10 per agent, unique; the API refuses a malformed tag (422)
and the console normalises as you type. The registry gains a repeatable `tag` filter with **AND**
semantics, applied after visibility. Each catalogue entry carries tags (the architect: `madr`,
`architecture`, `design`); install sets them, an **upgrade adds missing catalogue tags and never removes
one**; a fork copies its source's tags (a one-line amendment of ADR 0061). A migration backfills
platform agents from a map frozen in the migration. The console shows tags, filters by them, and edits
them (this also gives the agent's metadata an editor).

**Rejected.** Versioned tags (a tag edit would publish a version, change the checksum and make the
catalogue see every agent as changed). Curated categories as in the MCP and skills catalogues (the request
is labels an organisation chooses). A tag table with ids and colours. OR semantics. A tags endpoint (the
console counts client-side). No new ADR.

**PRs.** #617.

### Item 11 — Several global and several project memories at once

**Decision.** *An agent reads several memories, global and project, and writes to one.*
- **Named memory stores**: **global** (organisation-curated, with a reach: every project or a listed set)
  and **project** (curated by the project's owners). Two implicit project memories always exist and are not
  rows: `shared` (today's project memory) and `own` (the agent's own memory in that project).
- **The binding is a list on the version**: at most eight `{scope, slug, mode}`, no duplicates, **at most
  one write target**. A project reference is **relative to the run's project**, so an organisation agent
  reads the matching memory of whichever project it runs in. Order is precedence.
- **Compatibility without rewriting any version**: an absent list means "derive from the old setting"; the
  checksum leaves the new field out when null, so no existing checksum changes. Sending both is a 422.
- **Resolution per run** in an activity (no workflow change, no replayed history): an unresolvable binding
  is **skipped, never fatal** (memory never blocks a stage) and journaled as a run event.
- **Recall** queries each read memory concurrently and merges by a pure function: dedupe by subject with the
  highest precedence winning, then round-robin by precedence until the role's token budget is spent
  (scores from different stores are not comparable). Each item names its memory.
- **Writes** go to the single write target; a **global** write target only receives **proposals**, decided
  by an organisation administrator. Live search during a run reads the run's resolved read memories only.
- **Storage**: namespaces gain named-project and global forms; the old parser **refuses** the new forms so
  no adapter can read a named memory as the shared one; the lexical store gains an organisation key and a
  store key, with row-level security following the organisation.
- The review gap is closed: the project's memory pages take a memory selector, so an agent's own and named
  memories can be reviewed.

**Rejected.** A per-binding token budget. Several write targets (a fact written twice diverges). Absolute
references to another project's memory (promote it to global with a reach instead). An agent-wide "own"
memory across projects (it leaks between projects). Rewriting stored versions. Making an explicitly bound
memory's failure fatal (contradicts ADR 0007). Reusing knowledge bases for facts (ADR 0051 keeps them apart).

**PRs.** Contracts, API, storage #634 (ADR **0075**); runtime #640; console #651 (the definition view's
effective-bindings display is left to integrate with item 12's console).

**Left to the operator.** Nothing is required. An administrator may declare an organisation `memory`
connector to host global memories elsewhere than the deployment default; after the release, check that one
global-memory search returns without a client error in the API log.

### Item 12 — A readable agent definition, with a history

**Decision.** *An agent's history: versions with a message, compared field by field, restored as new.*
The console says **revision** (as in item 2); the API and the DSL keep **version**.
- A version carries a **message** (required by the new publish endpoint) and, for a restore, the version it
  came from. The platform writes messages for the versions it creates (created, catalogue install and
  update, fork).
- **Publish from a base**: a new endpoint takes the spec, a message and the base version; it answers 409
  `stale_base` when someone published since (naming the latest and its author) and 409 `no_change` when the
  checksum equals the latest. The old bare-spec endpoint stays. **Restore** copies version N byte for byte
  into the next version; nothing is ever rewritten or deleted.
- **Who uses a version** is read from the exposure endpoint of item 2 (one source of truth); until that
  merges, a list of the projects pinning it.
- **The diff is computed in the console** from two specs it already has, field-aware (instructions as a
  line diff, skills, tools, knowledge, memory bindings and eval cases by identity, unknown fields as JSON
  before and after), never by colour alone.
- **The page, by progressive disclosure**: **Definition** shows **one version, read-only, grouped** (a
  version bar, then folded groups with a one-line summary: About, Instructions, Model and runtime,
  Capabilities, Limits and budget, Eval suite; every field shown, none dropped). **Edit** is a deliberate
  mode: the builder based on the shown version, a live **Changes** panel, a required "what changed and why",
  and the stale-base and no-change messages. **History** replaces Versions: a timeline with messages,
  badges (current, restored from, pinned by, channels), compare any two, restore.
- "Restore" is never called rollback or promote: those words belong to items 2 and ADR 0061.

**Rejected.** A server-side working copy (a second state, locks, conflicts with the trial). A diff
endpoint (a pure function of two documents the client has). Changing the existing publish body (breaks
clients). The builder open by default (people read far more than they edit). A line diff of the JSON
(unreadable for lists).

**PRs.** API #630 (ADR **0076**); console #644.

## 4. What stays with the operator

The items that no repository change can finish, listed rather than asked:
- Merges into `main`, the releases that carry this stream, and the operator's deployment and platform
  repositories' merges and production synchronisations.
- Network rules on the operator's platform: allow the egress proxy's outbound hosts, then remove the
  runners' direct host rules; the sandbox operator and its network rule on every cluster that will use it.
- Settings of the GitHub App (setup URL, who may install it, events, OAuth during installation and its
  client secret in the operator's secret store).
- The organisation's network ceiling and the User-Agent contact.
- Browser checks that need a real session: the re-authentication bounce on a promotion, one live
  evaluation on a real model with a small budget.
- Decisions left to a maintainer: the built-in web tools default, the console bundle budget, the enterprise
  edition's compatibility range.
